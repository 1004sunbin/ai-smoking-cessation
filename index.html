    每一根 · 戒烟助手 Web 应用

    每一根都记下来，
    但一次复吸不让你从零开始。

    戒烟最难的是两个时刻：烟瘾冲上来的那几分钟，和抽了之后觉得"前功尽弃"的那一刻。这个项目围绕这两个时刻设计：烟瘾急救、复吸后继续陪伴，以及一个会查看记录、替你准备下一步的 AI 助手。

    打开应用无需注册，数据只存在你的设备上；想先看效果，可在设置里载入示例数据

    问题与目标

    观察到的问题

    • 多数戒烟 App 以"连续无烟天数"为核心，一次复吸就清零，用户容易就此放弃。
    • 烟瘾发作时，泛泛的建议（"坚持住"）帮不上忙，人需要一个马上能做的动作。
    • 不同的人、不同场景下有效的方法不一样，但很少有产品记录"什么对你有用"。

    产品目标

    • 帮用户撑过渴求高峰：按场景和强度给出一个具体动作。
    • 复吸后不清零：记录诱因、给出下一步，累计进度保持不变。
    • 每周给出一条可执行的建议，并追踪它有没有被用上。

    目标用户

    以下是设计时的用户假设，尚未经过用户访谈验证。

    想戒或想减量的成年吸烟者每天 10–20 根，尝试过戒烟但反复过；高频场景是饭后、工作压力和社交。
    核心需求烟瘾上来时有东西可以"抓住"；抽了之后不被责备；知道自己在哪些场景最容易失守。

    关键流程

    1. 设定目标选择"彻底戒烟"或"逐步减量"，填写每天支数和价格作为基线。减量模式每周目标比基线降低 20%。
    2. 一键记录"忍住了"一键记下，可撤销；"抽了一根"记录场景，可补记更早的时间。
    3. 烟瘾急救选场景和渴求强度 → 推荐一个动作并计时 → 结果（挺过去 / 还是抽了）→ 评价方法是否有效。
    4. 复吸后的下一步不评判；展示仍然有效的累计进度，并针对这次的诱因给出下次可以提前做的事。
    5. 每周回顾7 日趋势、与基线和目标对比、最有效的方法，以及"下周试试这一件事"。
    6. 找助手直接说"开会前很想抽"或"我又抽了"，助手查看记录、挑办法，给出可以一键执行的急救、计划、提醒卡片。

    AI 助手：从"会聊天"到"会做事"

    早期的 AI 陪伴只会回一段话。改成 Agent 后，模型可以调用 7 个工具，自己决定先看什么、再做什么：

    查看进度（今天抽了几根、累计少抽）；规律（高发场景、高发时段、急救成功率、哪些办法被评为有帮助）。
    挑选按场景和渴求强度，复用急救推荐算法，从 11 个动作里挑出最适合这个人的 3 个。
    准备急救、下周计划、定时提醒、记下这一根。只生成卡片，用户点了才执行，助手不会替人做决定。

    一条消息最多 4 轮工具调用、最多 2 张卡片。危机、急症和用药话题在调用任何工具之前就被浏览器拦下，使用固定回复。AI 连不上时，同一套工具按本地规则执行，助手依然可用。

    为什么不用数据库上一版曾在云函数里放 SQLite 保存用户画像。但云函数的本地磁盘随实例回收，数据会悄悄丢失，还和浏览器里的记录对不上。最后改为：记录只存在用户浏览器里，工具也在浏览器里执行，发给 AI 的只有统计结果。服务端只做转发，不保存任何内容。等到需要账号和跨设备同步时，再接托管数据库。

    差异点：会学习的烟瘾急救

    急救方法库有 11 个动作（慢呼吸、冲动冲浪、离开现场、刷牙、拒绝句等），每个动作标注适合的场景和渴求强度。推荐分数由三部分组成：

    得分 = 场景匹配（通用 +1 / 匹配 +3）
     + 强度匹配（在区间内 +2 / 否则 −2）
     + 个人效果（有帮助 +2、一般 +0.5、没帮助 −1.5；挺过去 +0.5、抽了 −0.5；同场景记录 ×1.5）

    用户评价越多，推荐越偏向"对这个人在这个场景下有效"的方法。用户关闭个性化授权后，只按场景和强度推荐。

    隐私设计

    • 所有记录、打卡和急救评价只保存在用户浏览器的 localStorage 中，不上传。
    • 助手默认由 AI 驱动，输入框下方写明由谁驱动；在设置中可一键关闭，改用本地规则。工具在浏览器里执行，只发送对话和工具算出的统计结果，不发送原始记录。
    • 涉及危机、急症和用药的话题始终在浏览器端使用固定回复，并给出 12356、120、12320 等求助渠道，不会发给 AI。
    • 设置中可以一键清除全部数据；演示数据单独标注，可随时重置或退出。
    一次取舍开发中曾尝试在前端直接接入云端大模型（Claude、硅基流动、Gemini）。纯静态页面调用这些服务必须把 API 密钥放在浏览器里，任何访客都能拿到，所以先撤掉了云端 AI。最终方案是加一个云函数转发：密钥只存在服务端；只接受本站调用；每位访客每天限 20 条；系统提示词和工具清单都在服务端固定，浏览器只能传对话、工具结果和几项统计数字，接口不能被拿去当通用聊天机器人；服务端不记录任何内容。

    技术方案

    前端原生 HTML / CSS / JavaScript，无框架、无第三方依赖，托管在 GitHub Pages。
    AI 助手阿里云函数计算（Python 标准库）转发到智谱 GLM 免费模型，使用函数调用（tool calls）；浏览器执行工具并把结果回传，最多 4 轮。主模型限流时切换备用模型，失败时退回本地规则。
    数据localStorage 单一状态对象，无服务器数据库；事件流（抽烟 / 忍住）带 id，支持撤销和补记；旧版数据自动迁移。
    统计口径"少抽的烟"= 基线 × 天数 − 实际记录，首页累计和周报共用同一个函数，避免数字互相对不上。
    界面移动端优先；暖白底、细线分隔、衬线数字，单一墨绿主色；深浅色模式，尊重"减少动态效果"系统设置。

    迭代记录

    1. v1 原型记录、恢复时间线、"一根烟"长按模拟：展示一根烟的焦油、尼古丁和一氧化碳。
    2. 烟品搜索每个人抽的烟不同，只有一个品牌时数字和用户无关。加入约 150 个国内外烟品规格的搜索，未收录的按常见标示估算并注明。
    3. 云端 AI 尝试与回退前端直连大模型有密钥暴露风险，先回退为本地规则（见隐私设计）。
    4. v2 重构把重心从"展示危害"转向"急救 + 复吸后陪伴"：急救按场景与强度推荐并收集效果反馈；复吸不清零累计进度；记录支持撤销和补记；修正减量目标和周报口径；加入可重置的示例数据（在设置中载入）。
    5. AI 陪伴上线加入云函数转发、限流和安全话题本地拦截。最初需要访客点击同意才开启，试用中觉得多了一步阻碍，改为默认开启、在聊天框下方说明并可在设置中关闭；测试中发现"胸口有点痛"这类说法没被识别为急症，扩充了识别规则，并在 AI 提示词里加了第二道保险。
    6. v3 Agent 与界面重做陪伴升级为能调用工具的助手：查看记录、挑办法、准备急救 / 计划 / 提醒卡片，由用户确认执行。撤掉了服务端 SQLite，数据和工具都留在浏览器。界面改为更克制的编辑风格，导航调整为今天、助手、进展、一根烟，"今天的预案"会在高发时段前主动提醒。

    数据说明与局限

    • 每根烟约减少 11 分钟预期寿命来自人群统计（Shaw 等，BMJ 2000）；恢复时间线参考 WHO 和美国 CDC。应用内的寿命、恢复和焦油数字都是估算，不代表个人医学结果。
    • 烟品焦油、烟碱、一氧化碳为包装标示的近似值，不同批次和市场会有差异。
    • 目前没有真实用户数据，演示数据为程序生成。下一步计划邀请 5 位吸烟者做可用性测试，关注三个指标：急救流程的完成率、急救后"挺过去"的比例、复吸后 7 天内是否继续记录。
